### KNOWN DEFECT (recorded for `sdd-verify`, deliberately NOT fixed in this apply — flagged by the orchestrator after live investigation, 2026-09-16)

**The C3 seed's idempotency key is structural, not semantic, and this produced a real (now-cleared) duplicate on the user's live database.** Before the eventual C9 reset, the live DB already held a `SPY` `CorporateEvent` created by an auto-detection mechanism (`"Detectado automáticamente (YAHOO_SPLIT)"`, real `createdByUserId`) at `effectiveDate: 2026-05-29`, `numerator/denominator: 3/1` — the SAME semantic fact (SPY's ratio change from 20:1 to 60:1) that the C3 seed also writes, at `effectiveDate: 2026-06-01`. `@@unique([instrumentId, effectiveDate, eventType])` did not catch this, because the two dates differ — the constraint (and the seed's own upsert key) is keyed on the literal tuple `(instrumentId, effectiveDate, eventType)`, not on "is this semantically the same corporate action." The result was two active `CorporateEvent` rows for the same real event. `applyEventsToTrade` (`src/lib/events/apply.ts:15`) applies each matching event's ratio multiplicatively per trade, so for the window this defect existed, every SPY trade dated before **both** effective dates was adjusted `×3 × ×3 = ×9` instead of the correct `×3` — a real, live valuation error on the user's actual holdings for however long that window lasted.

- **Root cause**: the seed's write path assumes it is the sole writer of "well-known" corporate actions. It has no way to detect that a DIFFERENT mechanism (the now-deleted `YAHOO_SPLIT` auto-detection code, confirmed gone from `src/` entirely — it would never have regenerated on its own) already recorded the same real-world fact under a different `effectiveDate`.
- **What actually happened this session**: the orchestrator discovered 3 `CorporateEvent` rows on the live (pre-reset) database, not the 1 this agent's C3 work assumed — 2 were `YAHOO_SPLIT`-authored (SPY at `2026-05-29` and a YPFD split), 1 was this seed's SPY row. All 3 were backed up to `corporate-events-backup.json` before the reset. The YPFD event was folded into `RECOMMENDED_EVENTS` (with a new required `instrumentType` field) so it survives future resets too; the duplicate SPY window no longer exists post-reset (the reset cleared both SPY rows and the seed now writes exactly one, cleanly).
- **Why this is not fixed here**: the reset already cleared the immediate symptom, or fixing the general case (making the seed's idempotency semantic rather than structural — e.g., de-duplicating by `(instrumentId, eventType)` regardless of date, or reconciling against effective real-world dates) is a design decision the user has not made, and is explicitly out of scope for C9's acceptance pass. **`sdd-verify` should treat this as a known, unresolved defect in the seed's idempotency model**, not as evidence C3's implementation itself is wrong per its own (narrower) task description — T-13 never anticipated a second, independent writer of the same semantic fact.

## Design correction found during acceptance: Docta's real rate limit (2026-09-16, post-C9)

**What was wrong**: AD-13's design text (and the briefing this apply session originally received) treated the 221 fixed-income `/instruments/` calls as "essentially free" / "zero marginal cost" — a whole-universe-per-run assumption. This was never independently verified before credentials existed; once they did, it turned out to be wrong by roughly two orders of magnitude.

**Measured, directly from a live HTTP 429 response** (2026-09-16, the same session as the C9 acceptance pass above):
```
x-dailylimit-limit: 15        x-dailylimit-remaining: 0
x-ratelimit-limit: 10         (per minute)
x-ratelimit-reset: 1789603200
retry-after: 63103
```
Docta's "basic" plan allows **15 requests/day** total (shared across every Docta endpoint — instrument metadata AND cashflow both draw on it) and **10 requests/minute**. This is why T-46/T-60/T-62/T-63's Docta-dependent measurements above found the quota already exhausted: a single `syncInstrumentCatalog()` run attempting all 221 tickers sequentially, plus a handful of diagnostic calls made earlier to isolate the trailing-slash 404 bug, burned roughly 18 hours of daily budget in under a minute.

**Two real bugs this exposed, both fixed**:
1. **`fetchDoctaInstrument` discarded a 404 instead of caching it.** On a 15/day budget this is not a style nit — it means every ticker Docta genuinely does not serve gets re-asked (and re-429'd, once the quota was already spent) on every single run, forever, competing with tickers that have never been asked at all. Fixed: a confirmed 404 is now cached permanently in `ScrapedBondData`, exactly like a successful response. Only a `429` (no evidence — the day's/minute's budget is spent) or a transport/parse error (no evidence — safe to retry later) are left uncached.
2. **The whole-universe, no-budget, no-ordering fetch loop** in `fixed-income-linking.ts` had no way to prioritize a user's actual holdings, and no way to stop once the quota was visibly spent — it would keep issuing (and 429-failing) a request for every remaining candidate.

**The fix, per the user's explicit decision (prioritize-then-drip)**:
- `src/lib/market/docta-linking-plan.ts` (+`.test.ts`, 8/8 passing) — a new **pure, unit-tested** module holding the ordering/budget-slicing decision: held instruments (referenced by ≥1 `Transaction`) are ordered first, unheld ones follow, and the result is sliced to a budget. `fixed-income-linking.ts` itself stays an untested Prisma orchestrator per convention — the decision logic does not live inside it.
- `src/lib/market/fixed-income-linking.ts` — now calls the plan module, adds `DOCTA_LINKING_BUDGET_PER_RUN = 8` (a sibling constant to `ENRICH_CONCURRENCY`/`ENRICH_BUDGET_MS` in spirit — deliberately placed in this file rather than physically next to those Yahoo-specific constants in `yahoo-catalog.ts`, since a Docta budget constant living in a Yahoo-named file seemed more confusing than clarifying; the design docstring cross-references both), paces live calls at one per `DOCTA_MIN_REQUEST_INTERVAL_MS = 6_500` (keeping the sequential loop under the measured 10/minute ceiling with margin), and stops the loop entirely — `break`, not `continue` — on the first `{ kind: "rate-limited" }` result.
- `src/lib/market/docta-client.ts` — `fetchDoctaInstrument`/`fetchDoctaCashflow` now return a `DoctaLookupResult<T>` discriminated union (`ok | not-found | rate-limited | error`) instead of `T | null`, so a caller can no longer conflate "confirmed absent" with "rate-limited" with "transport hiccup" the way a bare `null` forced it to. The previous 429-retry-with-backoff logic (added earlier this session, then found to hang for minutes against a real ~18h `Retry-After`) is removed entirely: against a *daily* cap, retrying within the same run cannot succeed, so `doctaGet` now reports `rate-limited` immediately, once, with zero wait. A new `hasResolvedDoctaInstrumentCache(tickers)` helper lets the orchestrator build the `needsDoctaLookup` flag `docta-linking-plan.ts` needs without spending a network call to find out.
- All three callers of the changed `fetchDoctaInstrument`/`fetchDoctaCashflow` signatures were updated: `docta-enrichment.ts`, `src/app/actions/bond-terms.ts`, and `fixed-income-linking.ts` itself.
- **Verified without spending live Docta calls**, per the coordinator's explicit constraint (the quota does not reset until ~2026-09-17 00:00 UTC): the new ordering/budget logic is covered by `docta-linking-plan.test.ts` (synthetic candidates, no fixtures needed — it is pure ordering/slicing arithmetic); the existing `docta-mapping.test.ts` (which does use the `__fixtures__/docta/` fixtures) still passes unchanged, confirming the mapping layer this change did not touch is unaffected.

**Artifacts amended**: `design.md` (AD-13 gained a "rev. 5 correction" subsection with the measured numbers and the prioritize-then-drip decision; §8's endpoint-path and cost/caching rows corrected), `spec.md` (FR-2 gained a budget-bounded/held-first requirement paragraph, a new Scenario FR-2-H for the exhausted-quota case, and the FR-2 acceptance-checklist line was extended), `tasks.md` (§5 measurements log row 6 records the exact headers; T-45's entry cross-references the correction).
